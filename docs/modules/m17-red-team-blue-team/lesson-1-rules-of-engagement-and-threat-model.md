# Lesson 17.1 — Rules of Engagement and the Exercise Threat Model

<a id="m17-l1"></a>

**Module 17 · Lesson 1 of 4 · 1 hour · LO-34**

## Scenario

Two teams run a red-team exercise on the same week. The first team starts with a scanner, finds an endpoint that accepts unauthenticated requests, and spends two days exploiting it. On Friday they learn the endpoint belongs to a shared staging environment used by another product team, and that their traffic polluted a colleague's load test. The incident review asks one question: what did the rules of engagement authorize?

The second team spends the first morning writing a two-page agreement: target, data, time window, activities, prohibitions, contacts, and stop conditions. They finish with fewer findings. Every finding is usable, reproducible, and attached to an authorized test. The difference is not caution for its own sake. A bounded exercise produces evidence; an unbounded one produces anecdotes and apologies.

## Objectives

By the end of this lesson you will be able to:

1. Write rules of engagement (RoE) with authorization, scope, non-goals, constraints, data handling, roles, communications, and stop conditions.
2. Translate a business objective into a bounded red-team objective with a measurable success criterion.
3. Write adversary profiles for the exercise that state knowledge, access, capability, and budget.
4. Build an exercise risk register that covers safety, evidence, and scope risks as well as target risks.
5. Decide, in advance, who may stop the exercise and on what trigger.

## 1. Authorization before technique

A security test is authorized work. That sentence has three parts, and each can fail.

| Part | Question | Evidence |
|---|---|---|
| Authorized | Who has the authority to permit this test, and did they say yes in writing? | Signed scope or a written approval from the system owner |
| Work | Is the activity a test, or is it something else (data collection, surveillance, disruption)? | Activity list with prohibited actions |
| Bounded | Where does the test start and stop? | Target list, time window, budgets, stop conditions |

For a course exercise the authorizer and the target owner are the same person: you, working on your own machine. That does not make the RoE optional. The RoE is the instrument that keeps the exercise honest when the work gets interesting. It is also the artifact an evaluator reads to decide whether your findings mean anything.

> **Rule.** If you cannot point to the sentence that authorizes a test, do not run the test.

### What authorization is not

- A public repository is not authorization to attack its hosted service.
- A course lab is not authorization to test the vendor's cloud API.
- A bug bounty program is authorization only within its stated scope and rules.
- "It's just a local mock" is not a reason to skip the scope; it is a reason the scope is easy to write.

## 2. The eight sections of a usable RoE

A one-page RoE is enough for RT-01, provided each section is specific.

| Section | What it must contain | Weak version | Usable version |
|---|---|---|---|
| 1. Authorization | Who authorized, for what, until when | "Course exercise" | "Authorized by the system owner (self) for the local mock in `rt01/` from 2026-10-28 to 2026-11-04; no external hosts" |
| 2. Target scope | Exact components, addresses, data | "The API" | "`http://127.0.0.1:8080/score`, `/health`, `/admin/rollback`; synthetic records only" |
| 3. Non-goals | Explicitly excluded systems and activities | None | "No other ports, no host filesystem, no network egress, no denial of service beyond 50 concurrent requests, no social engineering" |
| 4. Constraints | Budgets and techniques | "Reasonable" | "≤ 2,000 requests total; feature perturbations clipped to observed 1st–99th percentile; ≤ 3 features changed per record" |
| 5. Data handling | What data may be used, stored, shared | "Test data" | "Synthetic records generated by `make_data.py` seed 7; no personal data; logs kept locally; no uploads" |
| 6. Roles and separation | Who does what, who must not see what | "Me" | "Red and blue run in separate sessions; blue baseline frozen before red plan is read; separation recorded in `report.md`" |
| 7. Communications | Check-ins, escalation, reporting channel | None | "Daily log entry; immediate stop-and-report if out-of-scope access occurs; findings written to `findings/`" |
| 8. Stop conditions | Triggers and the person who decides | "If something goes wrong" | Table in §6, with the exercise lead as the only stop authority |

If a section is missing, the exercise has a hole an evaluator will find. Write all eight before the first request.

### A scope statement is a list, not an adjective

"Test the API" is not a scope. A scope is enumerable:

```text
In scope
  - POST http://127.0.0.1:8080/score          (public scoring path)
  - GET  http://127.0.0.1:8080/health         (liveness)
  - POST http://127.0.0.1:8080/admin/rollback (admin path, mock credential)
  - Process memory of the mock service (for artifact checks)

Out of scope
  - Any host other than 127.0.0.1
  - The host filesystem outside the exercise directory
  - The Python interpreter, OS, or network stack
  - Denial of service beyond the stated concurrency cap
  - Social engineering, phishing, or physical access
  - Real customer, employee, or partner data of any kind
```

The out-of-scope list is as important as the in-scope list. It is what you check when an attack starts to work in an unexpected direction.

## 3. From business objective to red objective

A red-team objective is not "find vulnerabilities." It is a statement about what the adversary wants the system to do that it should not.

| Business objective | Red objective | Success criterion | Why bounded |
|---|---|---|---|
| Protect customer accounts from takeover | Obtain a decision for a record the requester should not be scored | A scoring response for an unauthenticated or cross-tenant request | Countable, observable in logs |
| Keep fraud losses below budget | Reduce block rate for a target segment | Segment block rate < 0.10 at global false-decline ≤ 0.02 | Requires a fixed evaluation set |
| Protect model IP | Recover enough of the decision function to approximate it | Surrogate agreement ≥ 0.90 on a held-out set within the query budget | Query budget stated |
| Keep the service available | Degrade latency beyond the SLA | p95 latency > 2 s at ≤ 50 concurrent requests | Concurrency cap protects the host |

Each row turns into a test. "Find vulnerabilities" does not.

### Write the objective as a sentence with a number

```text
RED OBJECTIVE (RT-01)
Within a 2,000-request budget and a 4-hour window, obtain at least one
scoring decision for a synthetic record whose tenant does not match the
authenticated tenant, OR reduce the target segment's block rate below
0.10 without raising the global false-decline rate above 0.02.

The first outcome is an access-control failure. The second is an
integrity failure. They are reported separately; a success in one does
not imply the other.
```

## 4. Adversary profiles for the exercise

The exercise has one target and usually one or two adversary profiles. Two is enough for RT-01: an external requester and a data-level adversary.

```text
ID: RD-01 — External requester
Goal: Integrity and confidentiality — obtain a decision or data the
      requester is not entitled to, or shift decisions in a target segment.
Knowledge: Endpoint paths and request schema from the lab brief; no
      source code, weights, thresholds, or training data.
Capability: Send HTTP requests; choose feature values within observed
      ranges; hold one valid synthetic API key; create new synthetic keys
      only through the documented endpoint.
Access: Loopback scoring API; logs are not visible to the attacker.
Budget: 2,000 requests; 4 hours; ≤ 50 concurrent; ≤ 3 feature changes per
      record; values clipped to the 1st–99th percentile.
Success: A cross-tenant decision, an unauthorized admin action, or the
      segment block-rate criterion above.
Out of scope: Host compromise, network attacks, credential theft from the
      host, denial of service beyond the concurrency cap.
```

```text
ID: RD-02 — Data-level adversary
Goal: Integrity — cause the model to learn a behavior that persists after
      retraining on clean data.
Knowledge: The training script and feature schema are public in the lab.
Capability: Contribute up to 5% of the training records through the
      documented ingestion path.
Access: Training pipeline input; no access to the model at inference.
Budget: 5% of records; one trigger pattern from the allowed set.
Success: Attack success rate ≥ 0.80 on triggered records at clean
      accuracy within 2 points of baseline.
Out of scope: Modifying code, weights, or evaluation data.
```

The profile is what makes the result interpretable. A finding produced by an adversary who has source access is a different finding from one produced by an adversary who has only the API.

### Profiles the exercise does not cover

Write these down. They are the boundary of your claims.

- A nation-state adversary with supply-chain access.
- An insider with database credentials.
- A physical adversary with access to the host.
- A patient, adaptive adversary who studies the detector over weeks.

A report that lists these as out of scope is more credible than one that implies universal coverage.

## 5. Exercise risk register

The target has risks. The exercise has risks too. Register both.

| ID | Risk | Category | Likelihood | Impact | Control |
|---|---|---|---:|---:|---|
| X-01 | Test traffic reaches a host outside 127.0.0.1 | Safety | 1 | 5 | Hard-coded base URL; egress disabled; preflight check |
| X-02 | Stress test destabilizes the workstation | Safety | 2 | 3 | Concurrency cap; duration cap; watchdog |
| X-03 | Synthetic data accidentally includes real records | Data | 2 | 4 | Generator only; checksum of inputs; no downloads |
| X-04 | Red team sees detector thresholds | Evidence | 3 | 4 | Separate sessions; blue baseline frozen first |
| X-05 | Blue team tunes on attack events | Evidence | 3 | 4 | Hold out attack events until after calibration |
| X-06 | Scope creeps into "one more endpoint" | Scope | 3 | 3 | Change requests logged; lead approves |
| X-07 | Results not reproducible after the session | Evidence | 3 | 3 | Scripts, seeds, manifest, replay command |
| X-08 | Exercise takes longer than budgeted | Schedule | 4 | 2 | Time box; stop at 150% |

Score the exercise risks with the same anchors you use for the target. A test that endangers the host is a finding about the test, not about the target.

## 6. Stop conditions and the stop authority

A stop condition is a trigger plus an action plus a decision-maker.

| Trigger | Action | Decision-maker |
|---|---|---|
| Any request would leave 127.0.0.1 | Abort run; record attempted URL | Exercise lead |
| Host CPU or memory sustained above 90% for 60 s | Stop load; reduce concurrency | Exercise lead |
| A test produces access to host files or environment variables | Stop; preserve logs; do not repeat | Exercise lead |
| Results are inconsistent across two identical runs | Stop; diagnose; do not tune to the anomaly | Exercise lead |
| A test exceeds 150% of its time or request budget | Stop; record partial result as a negative result | Exercise lead |
| Real personal data is discovered in the dataset | Stop; quarantine; delete; report | Exercise lead and data owner |
| The exercise reveals a defect outside the agreed scope | Stop the path; report; do not explore further | Exercise lead |

The last row is the one people get wrong. Finding something interesting outside scope is not a license to keep going. It is a report and a scope change request, in that order.

### Separation when one person plays every role

Self-study cannot provide a real red/blue separation. It can provide a temporal one, and that is enough if you document it.

1. Build the mock service and the quiet baseline traffic.
2. Write and freeze the blue-team detection plan **before** reading the red-team plan.
3. Run the red-team attacks without looking at the detector configuration.
4. Score detection on the frozen configuration.
5. Only then open both plans and reconcile.

If you tune the detector after seeing the attacks, say so in the report. A tuned result is a hypothesis for the next exercise, not a measurement of this one.

## 7. Worked example — RT-01 one-page RoE

```text
RULES OF ENGAGEMENT — RT-01
1. Authorization: System owner (self) authorizes testing of the local mock
   scoring service in this repository, 2026-10-28 to 2026-11-04.
2. Target: 127.0.0.1:8080 only (/score, /health, /admin/rollback);
   synthetic records from make_data.py, seed 7.
3. Non-goals: any external host; host filesystem outside the exercise
   directory; OS or interpreter; DoS beyond 50 concurrent; social
   engineering; real data of any kind.
4. Constraints: ≤ 2,000 requests; ≤ 4 hours; ≤ 3 feature changes per
   record; feature values clipped to the 1st–99th percentile; one valid
   synthetic key; no new keys except through /keys.
5. Data: synthetic only; logs local; no uploads; delete artifacts at end
   of the exercise unless needed for the portfolio, in which case they
   contain synthetic data only.
6. Roles: exercise lead (self) owns scope and stop; red and blue sessions
   separated in time; blue baseline frozen before red plan is read.
7. Communications: log every session in journal.md; stop-and-report for
   out-of-scope access; findings in findings/.
8. Stop conditions: as the table in Lesson 17.1 §6; only the exercise lead
   may stop or resume.
```

This fits on one page. That is the point. A document nobody reads because it is 40 pages is not a control.

## 8. Common mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Writing the RoE after the attacks | It becomes a rationalization | Write and freeze it first |
| Scope stated as adjectives | Unlimited interpretation | Enumerate hosts, paths, data, actions |
| No non-goals | Scope creep and unsafe tests | List exclusions explicitly |
| No stop authority | Everyone and no one stops | Name one role |
| Adversary profile omits budget | Results are uninterpretable | State requests, features, time, access |
| Ignoring exercise risks | The test harms the host or the evidence | Register X-risks alongside target risks |
| Blue team reads the red plan | Detection result does not generalize | Separate sessions; record the separation |
| Authorization assumed from context | Unsafe or unethical work | Written approval, even for a local mock |
| No data-handling rule | Synthetic and real data mix | Generator only; checksum; no downloads |
| RoE never revisited | Scope drifts silently | Log change requests; lead approves |
