# Evaluator's Reference — Level 5 Projects

**For instructors and self-reviewers · Do not distribute before submission**

This guide supports assessment of the six projects, RT-01, and the capstone. It is not an answer key: the projects are open-ended, and a strong submission may reach a different conclusion from the reference expectations. The guide describes what evidence to look for, how to calibrate scores, and which failures are disqualifying.

> **Self-study use.** Read this only after submitting your artifact and self-scoring it against the rubric. Reading it first converts the project into a checklist and removes the judgment the assessment is meant to measure.

## 1. Assessment principles

1. **Judge the artifact, not the narrative.** A claim without a run record, table, or script is not evidence.
2. **A measured negative result is a result.** Do not penalize an attack that failed at a stated budget if the measurement is sound.
3. **One right answer does not exist.** Different defenses, thresholds, and segments are acceptable if justified and measured.
4. **Severity follows exposure.** A technically impressive attack with no plausible adversary is a low-severity finding.
5. **Reproduction is a gate, not a bonus.** If the headline number cannot be regenerated, the claim is unverified.
6. **Safety violations override technical merit.** A third-party target or real data is an automatic fail.

## 2. Scoring workflow

| Step | Time | Action |
|---|---:|---|
| 1. Safety screen | 5 min | Check targets, data, credentials, and authorized-use statement |
| 2. Structure check | 10 min | Confirm required artifacts exist and are readable |
| 3. Reproduction | 20–40 min | Run the one-command reproduction in a fresh environment |
| 4. Claim sampling | 20 min | Pick three claims; trace each to a table, run record, and script |
| 5. Rubric scoring | 15 min | Score each dimension independently before reading the reflection |
| 6. Feedback | 10 min | Two strengths, two fixes, one next step |

Score dimensions independently. Do not let a strong report raise a weak attack score, or a clever attack raise a weak limitations section.

## 3. Evidence triage

### A strong package

- `README.md` states the command, runtime, and expected headline number.
- `requirements.txt` and `environment.txt` are pinned and consistent.
- Data is generated by a script with a seed, or downloaded with a checksum and license.
- `run.json` links data, split, config, seed, and outputs.
- Results tables have denominators, budgets, seeds, and intervals.
- The report's numbers match the results files.
- Limitations name specific validity threats and their effect on the claim.
- The residual-risk statement names an adversary and a number.

### Red flags

| Signal | What it suggests | Check |
|---|---|---|
| Numbers in the report with no results file | Fabrication or manual editing | Trace the number to a run |
| Baseline "close enough" after a change | No frozen comparator | Compare hashes and thresholds |
| Attack success without a denominator | Uninterpretable claim | Ask "out of how many?" |
| Defense tested on one script | Static evaluation | Look for an adaptive variant |
| Best seed shown | Cherry-picking | Check per-seed appendix |
| No negative results | Story-shaped reporting | Ask what failed |
| Detector with no benign baseline | Detection theater | Check FP rate and threshold |
| Package built at the end | Unreproducible | Run clean checkout |
| Real names, IDs, or URLs | Safety violation | Stop and escalate |
| "Robust" or "secure" without a budget | Overclaim | Require a curve and a budget |

## 4. Project-specific reference expectations

The thresholds below are indicative. Students generate their own data, so absolute numbers vary; judge the relationship between baseline, attack, defense, and cost.

### PRJ-01 — Meridian Pay fraud

**Strong evidence**

- Duplicate audit changes recall; the change is reported with an interval and the original number is labeled optimistic.
- Evasion is bounded to observed percentiles and reported for a segment and globally.
- The monitoring gap is quantified: segment change vs global change.
- A preventive (duplicate gate or feature cap) and a detective (segment monitor) control are evaluated.
- False-decline and queue-volume costs are measured.

**Typical findings**

- Duplicate or near-duplicate disputes inflate reported recall.
- Segment-level evasion can be invisible in a global dashboard.
- Reviewer overrides are unlogged or under-specified.
- Feature caps reduce evasion but raise false declines.

**Common failures**

- Reporting a global block-rate change and missing the segment effect.
- Treating a threshold change as a defense without holding the evaluation set fixed.
- Measuring attack success without the false-decline constraint.

**Calibration notes**

- Exemplary: the data-quality finding changes the interpretation of the baseline, and the monitoring control is tested on the attack.
- Proficient: the attack and one control are measured with denominators; limitations are specific.
- Developing: experiments run but the segment/global distinction or the cost is missing.

### PRJ-02 — Aster Manufacturing poisoning

**Strong evidence**

- Poison and trigger rates are varied; clean accuracy and ASR are reported together.
- A zero-poison negative control is present.
- Screening is evaluated on clean and poisoned models, with false positives.
- An adaptive trigger (lower opacity, different location) is attempted.
- Retraining or fine-tuning is tested, and the residual ASR is reported.

**Typical findings**

- A small poison fraction can create a trigger behavior while clean accuracy stays within a few points.
- Screening catches the trained trigger but misses a lower-opacity variant.
- Clean fine-tuning reduces but does not eliminate the behavior.
- Screening has a false-positive cost on clean models.

**Common failures**

- Reporting ASR without clean accuracy.
- Screening tuned on the same trigger it is tested against.
- No negative control, so a high ASR could be a labeling artifact.
- Claiming removal after one fine-tune without an adaptive test.

**Calibration notes**

- Exemplary: the adaptive trigger changes the conclusion, and the defense's cost is measured.
- Proficient: poison curve, backdoor, screening, and one defense with a control.
- Developing: a demonstration without a defense or without a clean baseline.

### PRJ-03 — Helio Health privacy API

**Strong evidence**

- Extraction curve at three query budgets with a surrogate and a holdout.
- Membership inference at a low FPR, with a base rate and shadow-model design.
- Output formats compared on utility **and** leakage.
- Quota bypass with a second key tested.
- Log minimization evaluated.

**Typical findings**

- Exact scores or fine bands enable extraction; category-only output reduces agreement at a utility cost.
- Membership inference may be near chance on a small synthetic model; the interval must be reported.
- Per-key quotas are bypassed by a second key unless quotas are per tenant.
- Logs retain features that are not needed for accountability.

**Common failures**

- Reporting extraction agreement without the query budget.
- MIA accuracy without a base rate or FPR.
- Claiming DP for a model when only an aggregate release was noised.
- Ignoring the utility cost of output minimization.

**Calibration notes**

- Exemplary: a clear utility–leakage trade-off and a quota variant.
- Proficient: two attack measurements and one output control with cost.
- Developing: one attack, no utility comparison, or an unsupported privacy claim.

### PRJ-04 — Cobalt Models pipeline

**Strong evidence**

- Eight failure injections, each mapped to a gate and a block reason.
- A clean package passes every gate (false-reject check).
- Two fresh builds agree bit-for-bit or metric-for-metric within a stated tolerance.
- Signature and hash verification reject an altered artifact.
- Promotion fails closed without approval.
- Rollback is tested and timed.

**Typical findings**

- Schema checks pass renamed columns unless the check is explicit.
- Duplicate rows cross the split unless deduplication happens before splitting.
- An unapproved local wheel installs unless the allowlist is enforced at build time.
- A crash is not fail-closed; the gate must record a decision and stop promotion.
- Signing on the build host proves integrity relative to that host, not against a compromised host.

**Common failures**

- Testing only the happy path.
- Treating an exception as a controlled block.
- Verifying a good signature but never a bad one.
- Claiming reproducibility from the same environment.

**Calibration notes**

- Exemplary: the injection matrix exposes at least one fail-open behavior and the fix is verified.
- Proficient: six or more injections, clean false-reject check, reproduction and rollback.
- Developing: a pipeline that runs but is not adversarially tested.

### PRJ-05 — Harbor RAG/agent

**Strong evidence**

- Benign utility measured before attack results.
- Direct and indirect injections separated, with attack categories.
- A clean-document negative control.
- Tool authorization enforced in code, not only in the prompt.
- Approval gate tested with rephrasing and direct-call attempts.
- Two adaptive variants (encoded, split) attempted.
- Utility cost of controls reported.

**Typical findings**

- Retrieved text is followed as an instruction when the orchestrator concatenates it without provenance.
- Prompt-level instruction hierarchy reduces but does not eliminate indirect injection.
- Tool authorization in code blocks unauthorized calls even when the model proposes them.
- Approval can be bypassed if the tool is callable directly or the role check is missing.
- Aggressive filtering refuses benign questions; utility falls.

**Common failures**

- "Prompt injection solved" after one filter.
- Attack success measured without a benign utility baseline.
- Testing approval only by asking the model to skip it.
- Logging pasted text with identifiers.

**Calibration notes**

- Exemplary: code-enforced authority plus a measured utility trade-off and an adaptive variant.
- Proficient: injection tests, one context control, one authority control, utility measured.
- Developing: prompt-only mitigation or no benign baseline.

### PRJ-06 — Sentinel Vision robustness

**Strong evidence**

- Operating point defined before the comparison (threshold, FA target, FR limit, latency).
- Three defenses × three budgets × three seeds.
- ASR reported at the same operating point for every defense.
- Transfer and adaptive attacks; gradient masking considered.
- Cost table: clean accuracy, FA/FR, p50/p95 latency, training time.
- Recommendation uses pre-declared weights and states the trade-off.

**Typical findings**

- Adversarial training reduces static ASR but costs clean accuracy and training time.
- Squeezing helps at small ε and hurts at large ε; it may mask gradients.
- The adaptive attack recovers part of the ASR, changing the ranking.
- The latency budget rules out some defenses regardless of ASR.

**Common failures**

- Comparing defenses at different thresholds.
- Reporting only ASR.
- Omitting the adaptive attack.
- Claiming "robust" from one budget.

**Calibration notes**

- Exemplary: the adaptive result changes the recommendation, and cost is fully reported.
- Proficient: 3×3×3 comparison, cost table, adaptive attempt.
- Developing: one defense, one budget, or no cost.

### RT-01 — Red/blue exercise

**Strong evidence**

- RoE with eight sections and a named stop authority.
- Blue baseline frozen before the red plan is read; separation recorded.
- Seven attacks with budgets used and replay commands.
- Detection calibration with FP rate, recall, TTD, TTC, and a prevalence assumption.
- Containment followed by a benign-traffic replay.
- Two mitigations, a declared adaptive variant, and a residual-risk statement.
- Merged timeline with a gap that neither single-team report contains.

**Typical findings**

- The per-key quota and per-key detection miss a two-key actor.
- A detector fires late but recall is reported as 100%.
- Containment blocks benign dispatchers; the cost is unmeasured.
- The adaptive variant bypasses a static control.

**Common failures**

- Detector tuned on the test attacks.
- No benign baseline.
- Red and blue reports never merged.
- Reporting only successful attacks.

**Calibration notes**

- Exemplary: the merge produces a finding neither team saw, and the variant changes the mitigation assessment.
- Proficient: complete red and blue evidence, one mitigation replay, residual risk.
- Developing: attacks or detections in isolation, no synthesis.

### Capstone

Use the capstone rubric in the [capstone brief](capstone.md). The reference expectation is not a particular result; it is a complete chain from decision to threat to measurement to control to residual risk, reproducible from a clean checkout.

**Signs of an exemplary capstone**

- The question is narrow enough to answer and the answer changes a decision.
- The baseline is frozen and the negative control is present.
- An inconvenient result (failed attack, bypassed defense, null effect) is reported without spin.
- The adaptive variant is declared before it runs.
- The limitations section would satisfy a skeptical reviewer.
- The demonstration reproduces the headline number in front of the evaluator.

**Signs of an incomplete capstone**

- A topic rather than a question.
- Experiments without a baseline.
- A defense tested only statically.
- A report that argues rather than reports.
- A package that only works on the student's machine.

## 5. Rubric calibration examples

| Dimension | Score 4 looks like | Score 3 looks like | Score 2 looks like |
|---|---|---|---|
| Threat model | Adversary budgets drive test design; rejected risks have reasons | Profiles and register are complete; minor traceability gaps | Generic attacker; tests not tied to risks |
| Baseline | Frozen, hashed, controlled, reproducible | Reproducible with small fixes; no zero-effect control | Single run; no hash; threshold changed mid-stream |
| Attack | Multiple budgets; adaptive; honest negative | One budget; correct metrics | Metric errors; no denominator |
| Defense | Implemented; replay; variant; cost | Implemented; replay; limited cost | Proposed only, or static test |
| Reproducibility | Clean checkout; manifest; one command | Reproduces with fixes | Missing steps; environment unpinned |
| Communication | Claim-first tables; costed recommendations | Clear with minor issues | Narrative without evidence |

When two scores are plausible, choose the lower one and state what would raise it. That feedback is more useful than a generous mark.

## 6. Safety and integrity violations

| Violation | Action |
|---|---|
| Testing a third-party production system | Stop; automatic fail; notify the course owner |
| Real personal, payment, or health data | Stop; delete; automatic fail |
| Real credentials or keys | Stop; rotate if real; automatic fail |
| Distributing a malicious model or exploit | Stop; automatic fail |
| Fabricated or manually edited results | Automatic fail |
| Plagiarized report or code without attribution | Follow the institution's integrity policy |
| Scope exceeded within a local exercise | Deduct and require a corrected report; repeat violation fails |

A learner who discovers an unintended out-of-scope access must stop and report it. That is correct behavior, not a violation.

## 8. Reassessment

A failed dimension may be resubmitted once with a written change note that names the fix and the evidence. Reassessment uses a new clean checkout and the same rubric. A safety violation is not eligible for reassessment.
